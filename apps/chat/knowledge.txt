PROJECT NAME: BookMyService

1. PROJECT INTRODUCTION

BookMyService is an online service booking platform developed using Django.
It connects customers with service providers who offer everyday services.

Customers can create service bookings, receive offers from
providers, compare prices and ratings, and select a suitable provider.

Service providers can view relevant booking requests, submit offers, manage
accepted bookings, update work status, and maintain their profiles.

The platform uses authentication, role-based access, a database, Django
APIs, and frontend templates to manage its operations.

The BookMyService Assistant is an AI chatbot that explains platform
features and guides customers and providers through their workflows.

6. HOW TO VIEW MY BOOKINGS

Customers can view bookings associated with their authenticated account.

Typical workflow:
1. Log in as a customer.
2. Open My Bookings.

7. HOW TO CHECK BOOKING STATUS

BookMyService uses booking statuses such as:

PENDING:
The booking is awaiting further action. Depending on the workflow,
providers may still need to submit offers.

ACCEPTED:
A provider's offer has been accepted and the provider is assigned
to the booking.

IN PROGRESS:
The service provider has started the work.

COMPLETED:
The service work has been marked as completed.

REJECTED:
The booking has been rejected, or a related offer has been rejected.
Booking rejection and offer rejection are separate operations and
must be interpreted according to the relevant record.

How to check booking status:
1. Log in to the customer account.
2. Open My Bookings.
3. Locate the relevant booking.
4. Read its current status.
5. Open the booking details if more information is needed.

The chatbot can explain what each status means.

To answer a question such as "What is the status of my booking?",
the chatbot must:
1. Identify the authenticated customer.
2. Retrieve the customer's bookings from the Django API.
3. Identify the requested booking using its booking ID or other
   unambiguous details.
4. Read the current status from the API response.
5. Explain the result to the customer.

If multiple bookings match, ask the customer which booking they mean.



ChromaDB contains documentation, not automatically updated booking
records. Live status checks require database-backed API integration.


8. HOW TO CHECK PENDING BOOKINGS

9. HOW PROVIDERS VIEW AVAILABLE BOOKING REQUESTS

10. HOW TO SEND A PROVIDER OFFER

A service provider can submit an offer for a relevant booking.

Typical workflow:

3. Review the customer's requirements.
4. Enter the proposed service price.
5. Enter an optional message if supported.

7. The backend validates and stores the offer.

Example:

The example price is illustrative and is not an actual platform quotation.

If no offers are returned, the chatbot should explain that no offers
were found for the selected booking at the time of the API check.

The chatbot must not fabricate offers, prices, messages, or provider names.


12. HOW TO COMPARE PROVIDER OFFERS

Customers may compare offers using:
- Proposed price.
- Provider profile.
- Provider description.
- Provider rating.
- Service requirements.
- Offer message.

Recommended workflow:

2. View the offers received.
3. Compare the proposed prices.
4. Review provider profiles and ratings.

6. Choose the offer that best fits the customer's needs.

The lowest price is not necessarily the best option.

13. HOW TO ACCEPT AN OFFER

Customers can accept a suitable provider offer.

Typical workflow:
1. Log in as the customer who owns the booking.
2. Open the relevant booking.
3. View the available offers.
4. Select the preferred offer.
5. Confirm acceptance if the application requests confirmation.
6. The backend validates the operation.
7. If acceptance succeeds, the selected provider is assigned to
   the booking and its status is updated according to the workflow.
8. Other offers may be rejected automatically if this behavior is
   implemented by the application.

Only an authorized customer should be able to accept an offer
for their own booking.

The chatbot must use the appropriate authenticated API to accept
an offer. It must never claim acceptance succeeded without confirmation.

If the offer is no longer available or the operation fails, explain
the error returned by the application.


14. HOW TO CHECK AN OFFER'S STATUS

the status of the associated booking.

- Pending
- Accepted
- Rejected
- Completed

1. Open the relevant booking.
2. Open its offers section.
3. Identify the required offer.
4. Read the offer's current status.
5. Interpret that status separately from the booking status.

For example, an offer can be Accepted while the associated booking

Live offer-status checks require backend integration.

27. AVAILABLE BOOKINGS VERSUS AVAILABLE SERVICES

Available services are service categories configured in the application.

Available bookings are actual booking records that may be awaiting
provider offers or other action.

Provider availability refers to whether a suitable provider can take
a particular request.

These are three different concepts.

To answer "Which services are available?", retrieve the configured
service list when live data is required.

To answer "Which bookings are available?", query the booking API
using the authenticated user's role and permitted filters.

To answer "Is a provider available?", query an appropriate provider
availability source if the application implements one.

Never treat the knowledge base as a live availability database.

30. SECURITY AND AUTHORIZATION

The chatbot must follow these rules:

- Never reveal passwords, access tokens, or refresh tokens.
- Never bypass authentication.
- Never bypass Django permission checks.
- Never expose another customer's private booking information.
- Never expose provider or customer personal information without
  appropriate authorization.
- Never assume that a user is authorized based only on their message.
- Never allow a customer to perform provider-only actions.
- Never allow an ordinary user to perform administrator-only actions.
- Never claim that a database operation succeeded without confirmation.
- Never invent booking IDs, prices, offers, ratings, or user records.

All sensitive operations must be validated by the backend.
Frontend checks and chatbot instructions alone are not sufficient
to secure an API.


31. RAG AND CHROMADB

The BookMyService Assistant uses Retrieval-Augmented Generation (RAG).

The knowledge base contains documentation about the project, roles,
services, booking workflows, offers, ratings, and security rules.

The RAG workflow is:
1. Load the knowledge base.
2. Split the text into smaller chunks.
3. Convert the chunks into embeddings.
4. Store the chunks and embeddings in ChromaDB.
5. Convert the user's question into an embedding.
6. Retrieve the most relevant chunks.
7. Send the question and retrieved context to the LLM.
8. Generate an answer grounded in the retrieved context.

The embedding model used by the application is
sentence-transformers/all-MiniLM-L6-v2.

ChromaDB stores and retrieves documentation-based knowledge.

It does not automatically know the current state of Django database
records unless the application explicitly indexes and updates those
records. For live booking information, authenticated Django APIs
are the preferred source of truth.

34. FINAL PROJECT SUMMARY

BookMyService connects customers and service providers through
a service booking workflow.

Customers create bookings, receive provider offers, compare prices
and ratings, accept offers, monitor progress, and rate completed work.

Providers manage their profiles, review relevant requests, submit offers,
manage assigned work, update statuses, and view ratings.

Administrators manage users and services according to their permissions.

The BookMyService Assistant combines an LLM, embeddings, ChromaDB,
and RAG to explain the application and answer project-related questions.

Integration with authenticated Django APIs allows the chatbot to retrieve
live booking information and perform supported actions when implemented.

The knowledge base explains how the platform works, while the Django
backend remains the source of truth for live data, permissions, and
successful booking operations.
